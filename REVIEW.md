# REVIEW.md

Review of the starter `app/main.py`. "Reproduced" means I ran the original code and saw the symptom; "by inspection"
means it follows directly from the code (race conditions are hard to hit deterministically in a single process).
Every defect below is fixed in the submitted `app/main.py`.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` | Grace period is applied to the *floored* minutes (`minutes > 10`), so anything up to 10:59 after shift start counts as on time. | Reproduced: punch-in 09:40:01 on a 09:30 shift returns 0 (R2 says 10). | Compare whole seconds: late only if `delta_seconds > 600`, then `delta // 60` since shift start. |
| 2 | `compute_late_minutes` | Builds the shift start with `punch_in.replace(hour=..)` in whatever time zone the datetime happens to have. Not IST, and for an overnight shift the "start" is on the wrong calendar day. Sub-seconds are not truncated. | Reproduced: a UTC-aware punch-in at 09:50 IST (04:20 UTC) on a 09:30 shift returns 0 instead of 20. | Shift start is built as an IST datetime from the record's attendance `date`; instants are truncated to whole seconds first (R1). |
| 3 | `compute_work_hours` | `round()` is float/banker's rounding, R4 requires half-up. | Reproduced: 3h 01m 30s (3.025 h) gives 3.02 (want 3.03); 9630 s (2.675 h) gives 2.67 (want 2.68). | Exact `Decimal(seconds)/3600` quantised with `ROUND_HALF_UP`; `half_day` is decided on the rounded value (R5). |
| 4 | `compute_overtime` | No 30-minute minimum (R3); overnight shift end not moved to the next day; `int()` truncation and no time zone handling on punch-out. | Reproduced: out 18:35 on an 18:30 shift gives 5 (want 0); overnight 22:00-06:00 shift, out 06:40 next day, gives 1480 (want 40). | Shift end is IST on the attendance date (+1 day for overnight); floor minutes, kept only if >= 30. |
| 5 | `punch_in` (whole endpoint) | Unknown employee: `emp` is `None`, then `emp["shift_start"]` raises `TypeError`, a 500 instead of 404. | Reproduced: punch-in for `EMP9999` returns 500. | Explicit 404 lookup first. |
| 6 | `punch_in`: duplicate check | Check-then-insert (`find_one` then `insert_one`) with no unique index. Two simultaneous requests both pass the check and both insert. | By inspection: any two parallel identical punch-ins create two records for one (emp, day). | Unique index on `(emp_code, date)`; the insert itself is the guard and `DuplicateKeyError` becomes 409. |
| 7 | `punch_in`: timestamps | `punched_at` is treated as seconds/any number: `datetime.fromtimestamp(ms/1000)` gives a naive **server-local** time. `0` is treated as "not supplied" (`if body.punched_at`). Date comes from the local date, not IST. | Reproduced: `punched_at=1783312500` (seconds) is accepted and yields date `1970-01-21`; 00:30 IST on Jul 7 gets date `2026-07-06`. | Strict integer epoch-ms validated to 1e11..4.1e12 (else 422), converted to UTC-aware datetimes, truncated to seconds, date computed per R1 including overnight shifts. |
| 8 | `PunchInIn.status` | Any string accepted (including `ABSENT`, `LEAVE`, garbage); contract allows only `PRESENT`/`WFH`/`ON_DUTY`. | Reproduced: `status="ABSENT"` returns 201 with a punch-in time. | `Literal["PRESENT","WFH","ON_DUTY"]`; bad value is 422. |
| 9 | `punch_in` response | Returns `id` (the ObjectId) and raw datetimes; contract forbids `_id`/`id` and requires epoch-ms. | Reproduced: response keys include `id`; `punch_in` is a datetime. | `record_out()` serialises to the contract shape; every datetime goes out as epoch ms. |
| 10 | `create_employee` | Check-then-insert race and no unique index on `emp_code`: concurrent creates yield several 201s and duplicate employees. | By inspection (same pattern as #6). | Unique index on `emp_code`; `DuplicateKeyError` -> 409. |
| 11 | `EmployeeIn` | No validation at all: `emp_code` format, empty names, malformed e-mail, `shift_start == shift_end`, bad `HH:MM`, invalid `joined_on`. Bad shift strings blow up later in `split`/`int` (500). | Reproduced: `{"emp_code":"x","name":"","email":"nope","shift_start":"99:99","joined_on":"not-a-date"}` returns 201. | Pydantic constraints that mirror the OpenAPI patterns/lengths, real-date check, and a validator rejecting equal shifts. |
| 12 | `create_employee` | `created_at = datetime.now()` is naive server-local time stored as if it were UTC, and is returned as an ISO string rather than epoch ms. | Reproduced: response `created_at` is `"2026-10-10T10:48:23.214557"`. | UTC-aware `from_ms(now_ms())` stored as BSON date; returned as epoch ms. |
| 13 | `list_employees`: paging | `skip = page * page_size` skips the whole first page (should be `(page-1) * page_size`). | Reproduced: page 1 of size 2 returns the 2nd and 3rd employees. | `(page - 1) * page_size`. |
| 14 | `list_employees`: total, sort, bounds | `total` is `count_documents({})`, ignoring the department filter; no sort, so pages are not deterministic; `page`/`page_size` unbounded. | Reproduced: `department=Eng` reports `total` 7 (want 3); `page_size=100000` returns 200. | Count uses the same filter; sorted by `emp_code`; `page >= 1`, `1 <= page_size <= 100` (422 otherwise). |
| 15 | `list_attendance` | Loads the **entire collection** into Python, sorts and slices there. At 100k records this is slow and memory-hungry. Sort has no `emp_code` tiebreak, so pagination is unstable. | Reproduced by reading the code (`list(db.attendance_logs.find(q))`); symptom is latency/RAM growth with data size. | Filter, sort `(date desc, emp_code asc)`, skip and limit all in MongoDB, backed by indexes. |
| 16 | `list_attendance`: validation/shape | No date format or `date_from > date_to` check, no `status` enum, `page=0` gives a negative slice; returns `id` and raw datetimes; legacy docs without `half_day`/`history` are returned as-is. | By inspection. | Strict date validation (422), `Status` enum, bounded paging; `record_out()` applies defaults for legacy documents. |
| 17 | `GET /health` | Always returns ok; never touches MongoDB. The runner polls this to decide the app is ready. | Reproduced: returns `{"status":"ok"}` with the database unreachable. | Real `ping`; 503 on failure. |
| 18 | module level | No indexes are ever created (everything is a collection scan; uniqueness unenforced); `MongoClient` is created without `tz_aware` (naive datetimes everywhere) and never closed; database errors surface as 500. | Reproduced: no `create_index` or `close()` anywhere in the file. | Idempotent index creation at startup, `tz_aware=True` client, closed in the lifespan shutdown, `PyMongoError` mapped to a generic 503. |

## Looked at and judged not a defect

* `load_dotenv()` is called with the default `override=False`, so real environment variables already win over `.env` as the contract requires. Kept.
* Reading `MONGO_URI` / `MONGO_DB` from the environment with defaults is fine (nothing secret is hard-coded). Kept, with an `or` so an empty variable also falls back.
* `emp_code` as the lookup key (never `_id`) and `doc.pop("_id")` before returning: correct intent. The same idea is kept via `record_out`/`employee_out`.
* The 409 for a second punch-in on the same date is the right status; only the mechanism (#6) was wrong.
* Helpers are reusable in spirit (one function per rule), but none of the three could be reused as written (#1-#4); their signatures changed because late/overtime need the attendance `date`.
